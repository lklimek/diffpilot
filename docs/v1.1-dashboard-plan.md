## A. Where the scan runs

**Decision (ADR-017):** a server-side Rust port of `scan.py`/`stats.py`, run as a server task with the
signed-in user's GitHub App user token. The runner cannot hold that token (T3, OD6) and must not contain GitHub
client code. GitHub calls live in `server::github::work` (only `server::github` holds GitHub client code);
orchestration in `server::dashboard`.

Alternatives: (a) runner job with the user token — violates T3/ADR-005; (b) runner job with an installation
token + `github-mcp-server` — one installation cannot search "my work" across orgs, and an LLM-driven scan is
slow, non-deterministic and costly; (c) the Python skill as a sidecar — second runtime, no typed contracts.

### A.1 Token and reach
- Token: the user's App user-to-server token (`ghu_`, 8 h, refreshed through `auth::tokens`, serialised per
  user; ADR-007). S4: the token is the intersection of App and user access and reads public repositories without
  the App. **[A]** With the App installed where the owner works (OD7), search and details see everything he needs.
- **Reach diagnostic** (every refresh, one GraphQL alias query): each repository and enumerate-owner of the
  user's dashboard settings is looked up with the user token; one that is not visible becomes a scan note
  "Not visible to your GitHub token: owner/repo — install the GitHub App there or grant it access", and Settings
  shows the same mark on that row (from the latest snapshot).
- A 401 during a scan marks the token expired and refreshes once (ADR-007 addendum); a rejected refresh fails the
  refresh with "Sign in again".

### A.3 Rate limits, pacing, failures
- Searches: one at a time per user, ≥3 s apart (skill; S11-2: 3.5–4.6 s never tripped the secondary limit; 2 s
  not tried, so 3 s stays), retry on the secondary limit after `retry-after` or 60 s then 120 s, max 2 retries
  (never triggered in S11-2; tested against fake GitHub).
- Primary limit (`x-ratelimit-remaining: 0`) or a third secondary hit: the refresh fails with
  `retry_at = x-ratelimit-reset` ("Retry at 10:41"); the previous snapshot stays.
- Non-search calls ≤4 concurrent; one refresh per user at a time (T-2 index); whole refresh ≤5 min, else it fails
  as "took too long" with its log.
- Partial failures (one PR detail, one owner listing, a policy file, MemCan) do not fail the refresh: the item is
  dropped or marked and a scan note is recorded (skill §3 "What the scan missed").
- Volume, own + one linked login (S11-2 run: 100 candidate PRs, 2 issue repositories, 9 repositories). Skill: 24
  searches, 233 GraphQL calls (100 per-PR details + 131 hidden `gh pr list`), 48 REST calls; scan 109 s + stats
  56 s. Port: 12 scan searches + 6 history searches (issue statistics dropped), ~10 detail batches, 2–4 ref
  listings, 1–2 milestone, 1–2 history and 1 reach queries (≈20 GraphQL requests, ≈150 points), ~48 REST calls
  (38 paginated; files, releases, milestones). Target: scan **40–60 s** (paced searches dominate; details overlap),
  whole refresh ≈1–1.5 min, well inside the 5 min limit.
- **Reviews-given history on by default.** 120 s rule: if the real smoke in WP11-E2E measures a refresh over
  120 s, reviews-given history (one search per login) becomes off by default (code constant, no setting).

### A.4 Incremental refresh, cancellation, progress
- Discovery and details are always fetched live (CI changes do not bump `updatedAt`); incrementality is in the
  judgement (B): only new or changed items go to the LLM. Per-repo context is fetched once per refresh.
- Cancel: the refresh task holds a `CancellationToken` in `DashboardHub` (in-process, per user); it stops GitHub
  calls at the next await, cancels queued judge jobs, marks the refresh `cancelled`; the previous snapshot stays.
- Server restart: `scanning` refreshes become `failed` ("interrupted by a server restart"); unfinished judge jobs
  are cancelled and the ranking is marked interrupted (Retry ranking).
- Progress steps (mockup): `search_prs`, `issues`, `pr_details` (k/n + current item), `context` (ownership,
  milestones, reach), `history`, `todos`, `ranking` (judged/total), sent as `refresh` SSE events (E.3).
- Every refresh records its trigger (`manual` | `scheduled`); both use the same pipeline and the one-live-refresh
  rule: a start supersedes a refresh in `ranking` (its ranking ends `cancelled`) and is refused only while one
  scans (409 `refresh_running` for a manual start; a scheduled start counts as done); `docs/contracts/http-api.md`
  "Refresh states".

### A.5 Scheduled refresh (OD18, ADR-020)
- **Scheduler:** one tokio task in the server (`server::dashboard::schedule`), ticking every 60 s. The next run is
  never stored as a timer: each tick computes, from stored settings, whether a user is due — restarts lose nothing.
- **Due rule:** schedule on, time zone known, and for the user's current local date `d`: no scheduled run recorded
  for `d` (`last_scheduled_on`), local time ≥ the configured time, and no refresh (any trigger) finished
  successfully since today's scheduled instant. **Missed runs** (server down at 06:00) are caught up once at the
  first tick after start, still on the same local date; a past date is never caught up. A manual refresh after
  06:00 makes the scheduled run unnecessary (recorded as done, trigger skipped).
- **Time zone:** IANA name per user in the dashboard settings. The web sends the browser's zone
  (`Intl.DateTimeFormat().resolvedOptions().timeZone`) once, on the first dashboard visit while none is stored
  (R6b); Settings can change it. Until a zone is stored the schedule does not run and the dashboard says so.
  **DST:** the configured local time is resolved per date (jiff's bundled tz database; ADR-020 addendum "Time
  library"): a time in the spring-forward gap runs at the first valid instant after it; an ambiguous
  time (fall-back) runs at its first occurrence; one run per local date either way.
- **Stagger and limits:** at most one scheduled refresh runs at a time server-wide; due users are started in order
  of their due instant plus a fixed per-user offset (0–9 min, hash of the user id), so users configured at the same
  minute do not hit GitHub together. Each uses its own user token, so GitHub rate limits stay per user.
- **Token:** the stored, encrypted GitHub user-token pair and the v1 refresh path (serialised per user, ADR-007);
  ADR-020 keeps the pair while the schedule is on even without a live session. Refresh rejected, refresh token
  expired, or no pair (signed out everywhere) → the run is recorded `needs_sign_in` and the dashboard shows
  "Automatic refresh at 06:00 needs you to sign in again" until the next successful refresh.
- **Ranking:** a scheduled refresh submits `judge_work` like a manual one (only items needing judgement, §B.4);
  it waits behind a review analysis job (OD12).
- **Visibility:** scan info reads "Refreshed automatically at 06:00" or "Refreshed manually at 10:29"; the summary
  carries the last scheduled run (time, outcome, reason) and the dashboard shows its failure until a later
  refresh succeeds.

### B.2 How it runs
- **Decision (ADR-017, ADR-018):** job kind `judge_work` on the existing `JobExecutor`/runner path; a direct
  provider call from the server is not allowed (A3, A5). One-shot: `JobTarget::Dashboard { refresh_id }`, no
  checkout, no GitHub token, no MemCan endpoint, no session (nothing archived), no skills, priority
  `Interactive`.
- **Model/effort:** `select_model(JudgeWork, …)` returns the installation model with the installation-wide
  **dashboard ranking effort** (stored next to the model/effort choice, default `low`, editable in Settings;
  OD13). Other job kinds keep the saved effort. **[S-3]** checks that `low` judges acceptably and records the
  quality at `medium` for the owner.
- The prompt embeds the facts of up to **8 items** per job (fenced as data), the scoring legend and the anchors of
  skill §2; output schema `schemas/agent/judge_work.schema.json` (strict subset). Batches run one after another
  (one job per credential, ADR-003), giving "k of n judged".
- Input per item (≈ skill `score.py --template` `facts` + `hints`): id, kind, title, relations, author, labels,
  draft, CI effective + red checks, mergeable, review decision, threads, last comment, dependents, stacked-on,
  base/default branch and whether it is a release branch, milestone + context, linked issues, `bodyExcerpt`
  ≤300 chars, owned change, computed parts with basis, previous judgement (if inherited), suggested merges.
- Output per item: `id`, `likelihood`/`impact` (0–10, or null = no pre-existing defect), `change_impact`,
  `completion`, `urgency`, conditional parts (only if asked), `eligible` + `reason` (only if asked), `also_ids`
  (item keys),
  `alarm` (text or null), `why`, `next`, one short `basis` per judged part. The server re-validates (ids in the
  batch, closed value sets, text caps, `also_ids` ⊆ suggestions; stored as `ItemText.also_keys`); an invalid item stays provisional and is logged.
- Cost bound **[S-3]**: ≈8k input / ≈2k output tokens per batch; typically 5–15 changed/new items (1–2 jobs).
  Caps and the reuse rule: §B.4.

### B.4 Token saving (OD19; hard rule)
- **Judged-input fingerprint:** `SHA-256(JUDGE_INPUT_VERSION ‖ canonical JSON of the judged inputs)`. Judged inputs
  = exactly what the prompt shows that can change a judgement: kind, title, body excerpt (whitespace-normalised,
  300 chars), labels (sorted), draft, relations to the scanned logins, milestone title, linked issues (number,
  title), review decision, human change request present, unresolved-thread count class (0, 1–2, 3+), CI effective
  state + failing check names, mergeable, base = default / release branch, dependents and stacked-on ids,
  owned-change verdict, change-size class (<50, <200, <1000, <5000, ≥5000 lines), awaiting-our-reply flag,
  suggested merges; for TODOs status, priority, title, owner, `blocked_by` count and a hash of the description (MemCan
  has no `updated_at`, S11-4). Excluded (recomputed
  deterministically, never sent): `updatedAt`, every age (recency, request and comment ages), exact line counts,
  head SHA, comment counts, timeline times.
- **Rule:** same fingerprint + same prompt version → the stored judgement is reused at zero cost (status `judged`);
  different fingerprint → previous judgement shown as `inherited` (provisional) and the item is queued for
  judgement; no judgement → `unjudged`. Only queued items enter `judge_work` batches; **no job is created when
  nothing is queued**. This replaces the `updatedAt` fingerprint of the skill (a comment or push no longer
  re-judges an item unless a judged input changed).
- **Caps:** 48 items per refresh and 120 items per user per local day, counting every item **sent** to a judge
  job (retried, rejected, failed and superseded work included; reserved before each job, `sent` per refresh,
  migration 0008); Retry ranking and new refreshes do not reset them. An attempt stops after the first batch that
  ran out of retries. The remainder stays provisional, and the page names the limit that applied: "N items left
  provisional: this refresh's ranking limit (48)" or "… today's ranking limit (120)". Queue order: new items first, then changed items by provisional score.
- **Visible saving:** each refresh records `judged`, `reused`, `left_provisional`; scan info shows "judged 6 ·
  reused 31".
- **Prompt changes:** `JUDGE_PROMPT_VERSION` (prompt + output schema) is stored with every judgement. A golden test
  pins the prompt text to its version (hash), so editing the prompt fails CI until the developer either bumps the
  version (deliberate re-judging) or records the edit as non-semantic in the golden. The version check runs before
  the text comparison; only `RECORD_PROMPT_HASH=1` records a hash (`prompts/golden/judge_work.versions`), never
  `UPDATE_GOLDEN=1`. After a bump, older
  judgements count as `inherited` and are re-judged within the normal caps (spread over days, never all at 06:00);
  the dashboard shows "N items judged with an older ranking prompt". `JUDGE_INPUT_VERSION` changes the same way.

## C. Scoring

- **Placement:** `crates/server/src/dashboard/score/` — pure functions, no IO, no async; imports nothing from
  `db`, `github`, `memcan` or `tokio` (review rule). Not `analysis` (PR-diff analysis, runs `git`); no new crate
  (A12). Dependency rules hold.
- **Port:** `scoring.py` (components, formulas, CI classification, eligibility, milestone logic, PR/issue parts),
  `score.py` (merge rules, overrides need basis, provisional, tiers P1 ≥65 / P2 35–<65 / P3 <35 at full
  precision, sort score → advancement → severity → unblocks → id), `todos.py` `score_row`, `digest.py`
  `awaiting_others`/`ready_for_others`, the alias rule of §C.2.
- **Wire:** each part has `component` (closed enum of 12), `points_tenths: Option<i32>`, `source` (`computed` |
  `llm` | `not_applicable`), `status` (`computed` | `judged` | `overridden` | `inherited` | `estimated` |
  `pending`), `basis`. Totals as `total_tenths`; the tier is computed server-side and sent. Integers only on the
  wire (plan §5.3 "no float" rule intact).
- **States** (OD3): `final`; `provisional` (LLM parts `inherited` because the item changed, or a computed default
  awaits confirmation) — keeps its tier group, shown `~N`; `unjudged` (new item) — group "Not judged yet", `~N` =
  computed parts plus the constant estimates of §C.2 (status `estimated`; the basis names the rule, e.g.
  "estimate until judged: conventional type `docs` → 0").
- **Inheritance** (skill `inherit()`): judgements stored per (user, item key) with the judged-input fingerprint and
  prompt version of §B.4. Same fingerprint and version → judged parts kept; different → carried as `inherited` and
  re-judged; recency and size always recomputed; eligibility flips and
  `also_ids` carry while their targets exist; P0 alarms carry as provisional.
- **Tests:** port `test_scoring.py`, `test_score.py`, `test_todos.py`, `test_digest.py`, `test_milestones.py`
  cases as Rust unit tests (assert the contract); golden: archived `dp-scan.json` + `dp-judgment.json` → same
  order, tiers and breakdown as archived `scored.json` (rounding tolerance; settings = the skill defaults);
  proptest: sum = parts, tier monotonic in score, provisional never final.

### C.1 History for the charts
Computed at refresh time from GitHub (Q12–Q14) for a fixed window of **12 weeks** (60 working days for the
"4 weeks / before" tile and 12 weekly bars). The snapshot stores dated events `{kind, at, item_id}`
(`pr_opened`, `pr_merged`, `pr_closed_unmerged`, `review_given`; OD16), deduplicated across scanned logins
(OD14); the web buckets them by the browser's local day/week. The "Yesterday" panel shows PRs and reviews only. No accumulated history tables; the first refresh has the full window.

### E.5 REST architecture (whole dashboard API, consistent with v1)
| ID | Topic | Decision |
|---|---|---|
| E5-1 | Style | v1 models resources as collections with server ids (`/analyses/{id}`), control actions as `POST` verb sub-paths (`/pause`, `/resume`, `/cancel`, `/retry`), one SSE stream per resource (`/{id}/events`), and settings as `/settings` with `PUT /settings/<part>`. | E5-2 | Resources | `/dashboard` = per-user singleton summary; `/dashboard/items` = the ranked list of the latest snapshot (one `WorkItem` type for UI and agents; no UI-only composite); `/dashboard/refreshes/{id}` = one scan + ranking run. Item `key` is opaque and URL-safe, so `/dashboard/items/{key}` can be added later. |
| E5-3 | Versioning and additive change | `/api/v1` stays; changes follow ADR-011 (new field, variant, route or column; meanings never change). Breaking changes would get `/api/v2` next to v1. Clients are tolerant readers: ignore unknown fields, treat unknown enum values (`kind`, `component`, `status`, `tier`, `TokenScope`, history `kind`) as opaque. | E5-4 | Lists | R1b filters `tier`, `kind`, `repo`, `state`, `updated_since`; `limit` + opaque `cursor` (encodes `revision` and position); a cursor from an older revision answers 409 `cursor_expired` (rank order changes when judgements land). v1 lists stay unpaginated. |
| E5-5 | Cheap polling | R1 carries `revision` and `ranked_at`; agents poll R1 and fetch R1b only when `revision` changed; R1b also sends a weak `ETag` (hash of the body) and answers `If-None-Match` with 304. `Cache-Control: no-store` stays (session data), so shared caches keep nothing. |
| E5-6 | Errors | the v1 envelope `ApiError {code, message}` and status mapping unchanged; new codes in E.1. |
| E5-7 | Schemas for agents | v1 generates TS types (ts-rs) for HTTP DTOs and JSON Schemas (schemars) only for agent output. v1.1 also generates JSON Schemas for every `read` response type into `schemas/api/` (checked in, drift test) and documents the agent API in `docs/contracts/agent-api.md` (auth, routes, polling, tolerant-reader rule, examples). | E5-8 | Not blocked: token-triggered refresh | add `TokenScope::DashboardRefresh` and mark R2 `SessionCsrfOrToken(DashboardRefresh)`; a bearer request carries no ambient credential, so it needs no CSRF token. Additive: a new enum value, a route-auth change, no shape change. |

  `list_todos` (project required, optional status, limit 1–200, priority-then-age order, `has_more`).
- **Projects:** MemCan has no users and no project listing. Effective list per user = short names of the
  repository rows (`dashpay/platform` → `platform`; MemCan project = repository short name) plus the extra
  names of G17, deduplicated. An unknown project answers an empty list (shown as 0 open; typo and empty look alike).
- **Size:** ~0.8 KB per TODO, so 100 fit `MAX_ANSWER_BYTES` (256 KiB). `InvalidResponse` (over-size) retries once
  with limit 25, else a "too large" scan note for that project. Descriptions are cut to 500 characters, plain text.
- **Item mapping** (`kind = todo`):

| ID | MemCan field | Dashboard |
|---|---|---|
| M1 | `id` (UUID) | item key and link |
| M2 | `title` | title |
| M3 | `description` | detail, ≤500 characters, rendered as plain text; hash in the judged inputs (B.4) |
| M4 | `project` | group label (fact tag) |
| M5 | `priority` high/medium/low | rank input (`todos.py` `score_row`) |
| M6 | `status` | fact tag |
| M7 | `owner` | optional fact; no owner filter (mostly null) |
| M8 | `blocked_by` | "blocked by N" fact |
| M9 | `created_at` | age; no "last updated" claim |
| M10 | — (`completed_at` null for open rows) | not shown |

- **Change detection:** there is no `updated_at`. A TODO's change key = hash of status, priority, title, owner,
  `blocked_by` and description; its change time (R1b `updated_since`, list "changed" marker) = `created_at` on first
  sight, else the `scanned_at` of the refresh whose change key differs from the previous snapshot.
- **Links:** optional `SR_MEMCAN_UI_URL`, the user-facing UI base **including `/ui`** (e.g. `http://host:8190/ui`;
  not `SR_MEMCAN_URL`, the MCP endpoint); link `<SR_MEMCAN_UI_URL>/tasks/<uuid>`; without it, no links. The MemCan UI
  needs its own sign-in.
- Shown per user when "show my MemCan TODOs" is on (default on, OD10). Read-only (OD4).
- **Failures:** `Unreachable`/`Timeout` stop the remaining projects (`is_unavailable`); the refresh still finishes;
  TODO rows come from the previous snapshot, marked "not refreshed (MemCan unreachable at HH:MM)", with a scan note.
  A rejected token also surfaces as `Unreachable`, so Settings' MemCan status reads "MemCan unreachable or token
  rejected (check `SR_MEMCAN_TOKEN`)". `Rejected` (bad argument) is a scan note for that project.
