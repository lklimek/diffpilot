## A. Where the scan runs

**Decision (ADR-017):** a server-side Rust port of `scan.py`/`stats.py`, run as a server task with the
signed-in user's GitHub App user token. The runner cannot hold that token (T3, OD6) and must not contain GitHub
client code. GitHub calls live in `server::github::work` (only `server::github` holds GitHub client code);
orchestration in `server::dashboard`.

Alternatives: (a) runner job with the user token — violates T3/ADR-005; (b) runner job with an installation
token + `github-mcp-server` — one installation cannot search "my work" across orgs, and an LLM-driven scan is
slow, non-deterministic and costly; (c) the Python skill as a sidecar — second runtime, no typed contracts.

### A.1 Token and reach
- Token: the user's App user-to-server token (`ghu_`, 8 h, refreshed through `auth::tokens`, serialised per
  user; ADR-007). S4: the token is the intersection of App and user access and reads public repositories without
  the App. **[A]** With the App installed where the owner works (OD7), search and details see everything he needs.
- **Reach diagnostic** (every refresh, one GraphQL alias query): each repository and enumerate-owner of the
  user's dashboard settings is looked up with the user token; one that is not visible becomes a scan note
  "Not visible to your GitHub token: owner/repo — install the GitHub App there or grant it access", and Settings
  shows the same mark on that row (from the latest snapshot).
- A 401 during a scan marks the token expired and refreshes once (ADR-007 addendum); a rejected refresh fails the
  refresh with "Sign in again".

### A.3 Rate limits, pacing, failures
- Searches: one at a time per user, ≥3 s apart (skill; **[S-2]** may lower to 2 s), retry on the secondary limit
  after `retry-after` or 60 s then 120 s, max 2 retries.
- Primary limit (`x-ratelimit-remaining: 0`) or a third secondary hit: the refresh fails with
  `retry_at = x-ratelimit-reset` ("Retry at 10:41"); the previous snapshot stays.
- Non-search calls ≤4 concurrent; one refresh per user at a time (T-2 index); whole refresh ≤5 min, else it fails
  as "took too long" with its log.
- Partial failures (one PR detail, one owner listing, a policy file, MemCan) do not fail the refresh: the item is
  dropped or marked and a scan note is recorded (skill §3 "What the scan missed").
- Expected volume for own + one linked login **[S-2]**: ~14–16 searches, 5–10 GraphQL batches, ~20 REST calls;
  ≈1–1.5 min at 3 s spacing.

### A.4 Incremental refresh, cancellation, progress
- Discovery and details are always fetched live (CI changes do not bump `updatedAt`); incrementality is in the
  judgement (B): only new or changed items go to the LLM. Per-repo context is fetched once per refresh.
- Cancel: the refresh task holds a `CancellationToken` in `DashboardHub` (in-process, per user); it stops GitHub
  calls at the next await, cancels queued judge jobs, marks the refresh `cancelled`; the previous snapshot stays.
- Server restart: `scanning` refreshes become `failed` ("interrupted by a server restart"); unfinished judge jobs
  are cancelled and the ranking is marked interrupted (Retry ranking).
- Progress steps (mockup): `search_prs`, `issues`, `pr_details` (k/n + current item), `context` (ownership,
  milestones, reach), `history`, `todos`, `ranking` (judged/total), sent as `refresh` SSE events (E.3).

### B.2 How it runs
- **Decision (ADR-017, ADR-018):** job kind `judge_work` on the existing `JobExecutor`/runner path; a direct
  provider call from the server is not allowed (A3, A5). One-shot: `JobTarget::Dashboard { refresh_id }`, no
  checkout, no GitHub token, no MemCan endpoint, no session (nothing archived), no skills, priority
  `Interactive`.
- **Model/effort:** `select_model(JudgeWork, …)` returns the installation model with the installation-wide
  **dashboard ranking effort** (stored next to the model/effort choice, default `low`, editable in Settings;
  OD13). Other job kinds keep the saved effort. **[S-3]** checks that `low` judges acceptably and records the
  quality at `medium` for the owner.
- The prompt embeds the facts of up to **8 items** per job (fenced as data), the scoring legend and the anchors of
  skill §2; output schema `schemas/agent/judge_work.schema.json` (strict subset). Batches run one after another
  (one job per credential, ADR-003), giving "k of n judged".
- Input per item (≈ skill `score.py --template` `facts` + `hints`): id, kind, title, relations, author, labels,
  draft, CI effective + red checks, mergeable, review decision, threads, last comment, dependents, stacked-on,
  base/default branch and whether it is a release branch, milestone + context, linked issues, `bodyExcerpt`
  ≤300 chars, owned change, computed parts with basis, previous judgement (if inherited), suggested merges.
- Output per item: `id`, `likelihood`/`impact` (0–10, or null = no pre-existing defect), `change_impact`,
  `completion`, `urgency`, conditional parts (only if asked), `eligible` + `reason` (only if asked), `also_ids`,
  `alarm` (text or null), `why`, `next`, one short `basis` per judged part. The server re-validates (ids in the
  batch, closed value sets, text caps, `also_ids` ⊆ suggestions); an invalid item stays provisional and is logged.
- Cost bound **[S-3]**: ≈8k input / ≈2k output tokens per batch; typically 5–15 changed/new items (1–2 jobs).
  Hard cap 6 jobs (48 items) per refresh; the rest stay provisional with a scan note.

## C. Scoring

- **Placement:** `crates/server/src/dashboard/score/` — pure functions, no IO, no async; imports nothing from
  `db`, `github`, `memcan` or `tokio` (review rule). Not `analysis` (PR-diff analysis, runs `git`); no new crate
  (A12). Dependency rules hold.
- **Port:** `scoring.py` (components, formulas, CI classification, eligibility, milestone logic, PR/issue parts),
  `score.py` (merge rules, overrides need basis, provisional, tiers P1 ≥65 / P2 35–<65 / P3 <35 at full
  precision, sort score → advancement → severity → unblocks → id), `todos.py` `score_row`, `digest.py`
  `awaiting_others`/`ready_for_others`, the alias rule of §C.2.
- **Wire:** each part has `component` (closed enum of 12), `points_tenths: Option<i32>`, `source` (`computed` |
  `llm` | `not_applicable`), `status` (`computed` | `judged` | `overridden` | `inherited` | `estimated` |
  `pending`), `basis`. Totals as `total_tenths`; the tier is computed server-side and sent. Integers only on the
  wire (plan §5.3 "no float" rule intact).
- **States** (OD3): `final`; `provisional` (LLM parts `inherited` because the item changed, or a computed default
  awaits confirmation) — keeps its tier group, shown `~N`; `unjudged` (new item) — group "Not judged yet", `~N` =
  computed parts plus the constant estimates of §C.2 (status `estimated`; the basis names the rule, e.g.
  "estimate until judged: conventional type `docs` → 0").
- **Inheritance** (skill `inherit()`): judgements stored per (user, item key) with the fingerprint (`updatedAt` for
  PR/issue; `status|updated_at|len(description)` for TODOs). Same fingerprint and final → judged parts kept;
  different → carried as `inherited` and re-judged; recency and size always recomputed; eligibility flips and
  `also_ids` carry while their targets exist; P0 alarms carry as provisional.
- **Tests:** port `test_scoring.py`, `test_score.py`, `test_todos.py`, `test_digest.py`, `test_milestones.py`
  cases as Rust unit tests (assert the contract); golden: archived `dp-scan.json` + `dp-judgment.json` → same
  order, tiers and breakdown as archived `scored.json` (rounding tolerance; settings = the skill defaults);
  proptest: sum = parts, tier monotonic in score, provisional never final.

### C.1 History for the charts
Computed at refresh time from GitHub (Q12–Q14) for a fixed window of **12 weeks** (60 working days for the
"4 weeks / before" tile and 12 weekly bars). The snapshot stores dated events `{kind, at, item_id}`
(`pr_opened`, `pr_merged`, `pr_closed_unmerged`, `review_given`; OD16), deduplicated across scanned logins
(OD14); the web buckets them by the browser's local day/week. The "Yesterday" panel shows PRs and reviews only. No accumulated history tables; the first refresh has the full window.

## G. MemCan TODOs

- Read by the existing MemCan MCP client (`server::memcan::client`) in a new `server::memcan::todos`:
  `export_collection(collection="todos", limit=200, offset)` pages until a short page, parsed like `todos.py`
  (open statuses, refs, prefixes, day stats). Page size 200 keeps answers under `MAX_ANSWER_BYTES` (256 KiB).
  Tool name, page shape and fields (`id, project, title, priority, status, owner, blocked_by, created_at,
  updated_at, completed_at, description`) come from the skill **[A]**; **[S-4]** verifies them;
  `tools/fake-memcan` gains the tool.
- Links: optional `SR_MEMCAN_UI_URL` + `/tasks/<uuid>`; without it, no links.
- Shown per user when "show my MemCan TODOs" is on (default on, OD10). Read-only (OD4).
- MemCan down: the refresh still finishes; TODO rows come from the previous snapshot, marked "not refreshed
  (MemCan unreachable at HH:MM)", with a scan note; Settings' MemCan status reflects the call.
