## A. Where the scan runs

**Decision (ADR-017):** a server-side Rust port of `scan.py`/`stats.py`, run as a server task with the
signed-in user's GitHub App user token. The runner cannot hold that token (T3, OD6) and must not contain GitHub
client code. GitHub calls live in `server::github::work` (new file set; only `server::github` holds GitHub client
code); orchestration in `server::dashboard`.

Alternatives: (a) runner job with the user token — violates T3/ADR-005; (b) runner job with an installation
token + `github-mcp-server` — installation tokens are per installation and cannot search "my work" across orgs,
and an LLM-driven scan is slow, non-deterministic and costly; (c) keep the Python skill as a sidecar — second
runtime in the image, no typed contracts. Rejected.

### A.1 Token
- Token: the user's App user-to-server token (`ghu_`, 8 h, refreshed through `auth::tokens`, serialised per
  user; ADR-007). From code/S4: "token = intersection of App and user access; `scope` always empty"; the user token
  reads public repositories where the App is not installed (S4 `u12`: reads OK, writes FORBIDDEN).
- Unknown, **[S-1]**: (1) REST search with a user token across orgs where the App is not installed — expected:
  public results only; private results only from installations the user can access; (2) whether `is:pr`/`is:issue`
  is mandatory for App user tokens (community report says issues and PRs cannot be mixed in one query; the scan
  always sends one of them); (3) `review-requested:`, `mentions:`, `reviewed-by:` with a user token;
  (4) the "cannot be searched" refusal for `Claudius-Maginificent` with a user token; (5) GraphQL detail and REST
  files/releases/milestones/contents/events on non-installed public repos; (6) primary limits for user tokens
  (expected core 5000/h, GraphQL 5000 pts/h, search 30/min) and the secondary-limit response shape.
- A 401 during a scan marks the token expired and refreshes once (existing ADR-007 addendum path); a rejected
  refresh fails the refresh with "Sign in again".

### A.3 Rate limits, pacing, failures
- Searches: one at a time per user, ≥3 s apart (skill `SEARCH_MIN_INTERVAL_S`; **[S-2]** may lower to 2 s), retry on
  secondary limit after `retry-after` or 60 s then 120 s (skill `SEARCH_RETRY_WAITS_S`), max 2 retries.
- Primary limit (`x-ratelimit-remaining: 0`) or a third secondary hit: the refresh fails with
  `retry_at = x-ratelimit-reset` (mockup "Retry at 10:41"); the previous snapshot stays.
- Non-search calls: ≤4 concurrent per refresh; one refresh per user at a time (D.2 index). Budget: whole refresh
  ≤5 min wall time, then it fails as "took too long" with the partial log.
- Partial failures (one PR detail, one owner listing, ownership policy, MemCan) do not fail the refresh: the item
  is dropped or marked, and a scan note is recorded ("What the scan missed", skill §3 item 4).
- Expected call volume for one login + one linked login **[S-2]**: ~16 searches (Q1 ×6, Q10 ×4–6, Q12 ×5–10),
  5–10 GraphQL batches, ~20 REST calls; ≈1–1.5 min at 3 s spacing, within OD3.

### A.4 Incremental refresh, cancellation, progress
- Discovery and details are always fetched live (cheap after batching; CI changes do not bump `updatedAt`).
  Incrementality is in judgement (B): only new or changed items (fingerprint) are sent to the LLM.
- Per-repo context (releases, milestones, ownership policy) is fetched once per refresh.
- Cancellation: the refresh task holds a `CancellationToken` in `DashboardHub` (in-process, per user); Cancel
  stops GitHub calls at the next await, cancels queued judge jobs, marks the refresh `cancelled`; the previous
  snapshot stays (mockup "Cancel scan").
- Server restart: at start, `scanning` refreshes become `failed` ("interrupted by a server restart"); unfinished
  judge jobs of `ranking` refreshes are cancelled and the ranking is marked interrupted (Retry ranking).
- Progress: steps of the mockup — `search_prs`, `issues`, `pr_details` (k/n + current item), `context` (ownership,
  milestones), `history`, `todos`, `ranking` (judged/total) — sent as `refresh` SSE events (E.3); bar percentage
  = processing progress (allowed on the dashboard, OD2).

### B.2 How it runs
- **Decision (ADR-017, ADR-018):** a new job kind `judge_work` on the existing `JobExecutor`/runner path. A
  direct provider call from the server is not allowed (A3, A5: only `runner::provider` knows Codex; the server
  has no Codex). The job is one-shot: `JobTarget::Dashboard { refresh_id }`, no repository checkout, no GitHub
  token, no MemCan endpoint, no session (`session`, `working_session`, `context_pack` = none; nothing archived),
  no skills; priority `Interactive`; `select_model(JudgeWork, …)` = installation model at **low** effort
  (ADR-017; **[S-3]** decides low vs medium; Q11-5).
- `JobSpec` is self-contained: the prompt embeds the facts of up to **8 items** per job (fenced as data, never
  instructions), the scoring legend and the anchors of skill §2; output schema `schemas/agent/judge_work.schema.json`
  (strict subset). Batches run one after another (one job per credential, ADR-003), giving "k of n judged".
- Input per item (≈ skill `score.py --template` `facts` + `hints`): id, kind, title, relations, author, labels,
  draft, CI effective + red checks, mergeable, review decision, threads, last comment author/age, dependents,
  stacked-on, base/default branch, milestone + context, linked issues, `bodyExcerpt` ≤300 chars, owned change,
  computed parts with basis, provisional defaults, previous judgement (if inherited), suggested merges.
- Output per item: `id`, `likelihood`, `impact` (0–10 or null = no pre-existing defect), `change_impact`,
  `completion`, `urgency`, `blocked` (only if asked), `unblocks`/`human_waiting`/`advancement`/`milestone` (only
  if asked), `eligible` + `reason` (only if asked), `also_ids`, `alarm` (string or null), `why`, `next`, and one
  short `basis` per judged part. Server re-validates: ids belong to the batch, values in the closed sets of
  `scoring.COMPONENTS`, text lengths capped, `also_ids` ⊆ suggestions; an invalid item stays provisional and is
  logged (no repair run).
- Cost bound **[S-3]**: ≈700 input tokens per item + ≈2k prompt → ≈8k input / ≈2k output per batch; a typical
  refresh judges 5–15 changed/new items (1–2 jobs). Hard cap 6 jobs (48 items) per refresh; the rest stay
  provisional with a scan note.

## C. Scoring

- **Placement:** `crates/server/src/dashboard/score/` — pure functions, no IO, no async; it imports nothing from
  `db`, `github`, `memcan` or `tokio` (review rule). Not `analysis`
  (that crate is PR-diff analysis and runs `git`); no new crate (A12; only the server uses it). Dependency rules
  hold: `server → contracts`.
- **Port:** `scoring.py` (COMPONENTS, LEGEND, recency/size/waiting/unblocks formulas, CI classification with
  `POLICY_CHECK_RE`, `PSEUDO_BOTS`, eligibility, milestone version logic, PR/issue parts) and `score.py`
  (merge rules, overrides need basis, provisional, tiers P1 ≥65 / P2 35–<65 / P3 <35 with full precision, sort
  key score → advancement → severity → unblocks → id), `todos.py` `score_row`, `digest.py` `awaiting_others`
  and `ready_for_others`, repo aliases (`REPO_ALIASES` table + derivation). Owner-specific vocabularies stay
  code constants as in the skill (Q11-6).
- **Wire:** every part is sent with `component` (closed enum of 12), `points_tenths: Option<i32>`, `source`
  (`computed` | `llm` | `not_applicable`), `status` (`computed` | `judged` | `overridden` | `inherited` |
  `pending`), `basis` (server text for computed parts; LLM text for LLM parts). Totals as `total_tenths`; the tier
  is computed server-side at full precision and sent (no client threshold). Integers only on the wire (keeps the
  contracts "no float" rule of plan §5.3 intact).
- **States** (OD3): `final` (all parts settled); `provisional` (some LLM parts `inherited` from an earlier
  judgement because the item changed, or a computed default awaits confirmation) — keeps its tier group, shown
  `~N`; `unjudged` (new item, LLM parts `pending`) — group "Not judged yet", `~N` = computed parts only.
- **Inheritance** (skill `inherit()`): judgements are stored per (user, item key) with the item fingerprint
  (`updatedAt` for PR/issue; `status|updated_at|len(description)` for TODOs). Same fingerprint and final → every
  judged part kept (`judged`); different fingerprint → judged parts carried as `inherited` (provisional) and the
  item is re-judged; recency and size are always recomputed; eligibility overrides and `also_ids` carry while
  their targets exist. P0 alarms carry as provisional.
- **Tests:** port the cases of `test_scoring.py`, `test_score.py`, `test_todos.py`, `test_digest.py`,
  `test_milestones.py` as Rust unit tests (assert the contract, not the code); golden: archived
  `dp-scan.json` + `dp-judgment.json` → same ranked order, tiers and breakdown as archived `scored.json`
  (tolerance: rounding only); proptest: sum = parts, tier monotonic in score, provisional never final.

### C.1 History for the charts (decision with D)
Computed at refresh time from GitHub (Q12–Q14) for a fixed window of **12 weeks** (covers 60 working days for the
"4 weeks / before" tile and 12 weekly bars). The snapshot stores raw dated events `{kind, at, item_id}`
(`pr_opened`, `pr_merged`, `pr_closed_unmerged`, `issue_opened`, `issue_closed`, `review_given`, `todo_new`,
`todo_done`, `todo_cancelled`), deduplicated across linked logins; the web buckets them by the browser's local
day/week (no server time-zone dependency; skill used Europe/Warsaw). Backfill is inherent (first refresh has the
full window); no accumulated history tables. Issue counting: authored or assigned to a scope login (Q11-7).

## D. Data model

### D.1 Tables (migration `NNNN_dashboard.sql`, additive; number assigned at merge, H4)

- **Snapshot vs normalised:** snapshot document per refresh. The page reads one user's whole list at once; no
  query spans items across users or snapshots except inheritance, which `dashboard_judgements` serves.
  Normalised item tables were rejected (more schema, no query needs them).
- **Retention:** last 10 refreshes per user (older rows deleted at refresh start); judgements not seen for
  30 days deleted; judge jobs follow the v1 job retention.
- **Scoping:** every repository function takes `(tenant_id, user_id)`; no list-all API. Dashboards are per user in
  the multi-user tenant; linked logins only widen what one user's scan searches.
- **Privacy:** titles, labels and 300-char body excerpts of private repositories the user token can read are
  stored in snapshots and in judge job prompts (`jobs.spec`). New threat-model entries T16–T19 (§E.4).
