## 2. Webhooks (ADR-026)

### 2.1 Path and endpoint
GitHub → Cloudflare WAF (GitHub `hooks` ranges only) → atlas tunnel → traefik (Host rewritten, real IP only in
`Cf-Connecting-IP`) → `POST /webhooks/github` (public URL `https://webhooks.manago.cloud/diffpilot/github`).
Route `githubWebhook` in `ROUTES` with a new `RouteAuth::GithubSignature` (contract change: the auth matrix tests
classify every route). Not under `/api/`, no session, no CSRF, never a personal access token.

| ID | Rule |
|---|---|
| W1 | **Order:** method POST only → body limit **4 MiB** (413; subscribed events are far smaller; GitHub's own cap is 25 MB) → headers `X-GitHub-Event`, `X-GitHub-Delivery` (UUID), `X-Hub-Signature-256` present (else 400) → HMAC-SHA256 of the raw bytes with the secret, `sha256=` prefix, constant-time compare (`aws_lc_rs::hmac::verify`, already a server dependency) → 401 on mismatch, no detail → only then parse JSON. IPs are never used for auth. |
| W2 | **Dedupe and durability:** in one write transaction insert `github_deliveries(delivery_id, …, state='pending')`. Existing row in `done`/`ignored` → 200, nothing else (duplicate). Existing `pending`/`failed` → processed again (GitHub redelivery reuses the delivery id, so a failed processing must stay retryable). |
| W3 | **Fast ack:** the handler stores the delivery's typed `WebhookChange` list (extracted from the payload at receipt: repo, number, kind, head SHA, action, installation) — never the raw payload — answers **202** and wakes the worker (tokio `Notify`). Target < 1 s; GitHub's limit is 10 s. |
| W4 | **Worker:** one in-process task drains `pending` rows oldest first, retries a failed row 3× with backoff (10 s, 1 min, 10 min), then `failed` (warn once). At start-up it resumes `pending`/`failed` rows younger than 3 days. |
| W5 | **`ping`:** 200, `ignored`, info log with hook id. Unsubscribed or unknown events: 202, `ignored`, debug log. |
| W6 | **Concurrency:** at most 8 requests in the handler (tower `ConcurrencyLimitLayer`; 503 beyond, GitHub records a failure and the sweep redelivers). |
| W7 | **Logging/audit:** info per accepted delivery (`delivery_id`, event, action, repo, number, outcome `queued`/`duplicate`/`ignored`); warn on signature failure with `Cf-Connecting-IP` as data, at most once a minute (counter in the message); never the body, signature or secret. Rows kept 14 days (pruned by the nightly task); `GET /api/v1/settings/github-webhook` shows the last verified delivery time. |
| W8 | **Secret config:** `SR_GITHUB_WEBHOOK_SECRET` (secrets.env, ≥ 32 characters, `SecretString`) and `SR_GITHUB_WEBHOOK_URL` (https, display only). Both or neither (start-up error otherwise); neither = route answers 404 and no repository is live. Rotation: change both sides; deliveries failing meanwhile are redelivered by the sweep (W11). |

### 2.3 Processing (idempotent signals, never state)
An event is a signal "re-read this"; processing always re-reads GitHub, so order and duplicates do not matter
(cost only). Per user, signals are coalesced for 10 s, then:

| ID | Rule |
|---|---|
| P-1 | **Affected users:** users whose current snapshot holds the PR/issue (SQLite `json_each` over the current snapshots; few users; add an index table only if profiling asks). Check/status events match `StoredPr` by head SHA. |
| P-2 | **Dashboard:** `reread` of those PRs (existing path, user token, `REREAD_LIMIT`, rate-limit memory), extended to issues (B3). Facts only (P3): the snapshot changes, the judgement's fingerprint no longer matches → *outdated* (§4). |
| P-3 | **New items (OQ4 = b):** E1 `review_requested`/`assigned`/`opened` naming a linked login of a user, for a PR not in the snapshot → read that PR as a scan candidate with the relation the event shows, add it, then `rank_pending` judges it (new item, P3). |
| P-4 | **Review loop:** a watched PR (any watcher) gets the watch probe at once (the same path a plug-in change signal uses), so a pass becomes due by the existing rules (bot-round wait, spacing, daily cap). Unwatched PRs: nothing (Comments reads on demand). |
| P-5 | **Live set:** E9 upserts/removes `app_repositories`; `suspend` marks suspended. A daily sync (nightly task) and a lookup when a snapshot names an unknown repository use `GET /repos/{o}/{n}/installation` (App JWT, `github/app_token.rs:224-244`) — no new token type. |
| P-6 | **Live:** a repository is live when the webhook is configured (W8) and it is in `app_repositories`, not suspended. TODO items have no `live`. |

### 2.4 Missed events
| ID | Rule |
|---|---|
| W9 | Our processing failure: W2/W4 (row stays retryable; redelivery reprocesses). |
| W10 | Server down: GitHub records failed deliveries; at start-up the sweep (W11) redelivers them. GitHub keeps deliveries for redelivery for 3 days. |
| W11 | **Sweep:** `GET /app/hook/deliveries?status=failure` (App JWT, cursor pagination, newest first) back to the last sweep's mark (stored in `github_delivery_sweep`), `POST /app/hook/deliveries/{id}/attempts` for each whose GUID is not `done` here. Runs at start-up and **every 30 min** (OQ1): one REST call when nothing failed, no user token, no LLM. |
| W12 | Beyond 3 days or a bug: the nightly scan and manual Refresh are the backstop (P2 already relies on them). |

## 4. Judgement model (C1, C2, G2)

| ID | Rule |
|---|---|
| J1 | **Queue** (every ranking: manual, nightly, webhook, re-judge): asked items **never judged** (no stored body), plus items with a re-judge request, plus — only for `rejudge_outdated` — every outdated item. Changed items are no longer queued (replaces F-3). Order: requests first, then new by provisional score. |
| J2 | **Outdated:** a stored judgement that is not fresh; `prompt_changed` when prompt or input version differ (`older`), else `facts_changed`. It keeps scoring as `Inherited` (today's behaviour). |
| J3 | **Re-judge request:** `dashboard_judgements.rejudge_requested_at` (B1 migration). Set by C2 (one item) or by `rejudge_outdated` (all outdated); cleared when the new judgement is saved (the row is replaced). Persisting it survives restarts and makes `judging` derivable. |
| J4 | **Ranking without a scan** (`refresh::rank_pending(scope)`): when nothing is live, restart the ranking of the current snapshot's refresh in a new attempt (F-5 widened to rankings that ended `finished`); when a ranking is live, it **drains**: before finishing it re-reads pending requests and new items and judges them in the same attempt. Used by C2, webhooks (P-3) and the end of a re-read that added items. |
| J5 | **States:** current = fresh; judging = request pending and a ranking live; outdated = not fresh otherwise; queued = never judged and a ranking live; capped = never judged and in the latest ranking's left-provisional keys (stored in `RefreshProgress.left_provisional_keys`, serde default, no migration); not_judged = never judged otherwise. |
| J6 | **Nightly** (ADR-020) uses J1 without `rejudge_outdated`: it judges only never-judged items (U19). A prompt bump makes every judgement `prompt_changed`, re-judged only by click or "Refresh and re-judge outdated". |
| J7 | **Counts:** `status_counts` from the scored items: outdated (J5 outdated + judging), not_judged (queued + capped + not_judged), not_live (C3), excluded (existing exclusions total). |

## 6. Needs you (C10) and duplicates (C15)

**N1 Item status** — a Rust port of `web/src/components/comments/queueStatus.ts` `commentStatus` (first match wins);
`awaits` = not gone and state ∈ {undecided, reopened, asked_back}; `linked` = `duplicate_of` set and ≠ own number:
1. `status_comment` → StatusComments
2. current decision `ImportedGithub`, or state `outside` → Decided
3. `decision_follows_primary` (linked, no gates) → Duplicates
4. state ∈ {decided, executing, done, repeat} → Decided
5. gone → All
6. linked and (awaits, or gates non-empty and state `assessing`) → **NeedsYou** (unassessed linked items without C15 count)
7. assessment Queued → Waiting; 8. Running → Assessing
9. kind ≠ `pr_question` and NotAssessed → NotAssessed (unassessed unlinked items do not count)
10. awaits → **NeedsYou**, else All

**N2 Count** = Σ over the overview's queue entries of their items whose status is NeedsYou (items outside the queue
never count, as `needsYouQueue`); `needs_you_gates` = those with gates. One function in `review_loop::queue`
feeds `CommentCounts`, the PR page summary, badge B2 and the dashboard tally (F-6 SQL keeps `total`, `was_read`,
`watched`; `needs_you` is computed from the loaded views of the listed PRs that were read).
**N3 Drift guard:** a checked-in fixture `docs/contracts/fixtures/needs-you-cases.json` (items, queue → expected
status per item and count) runs in a Rust test and a vitest test; B14 points the web at the server count.

**N4 Status comments (F1/F2 of 07b69073):** an item from the source fallback (F-7) whose author is a bot — `Bot`
typename, `[bot]` login or `known_bots` (fixes F2: today `__typename` is ignored there) — of kind `pr_comment`, with
no finding markers (`markers::body_findings` empty, no `finding_marker`), is stored with `status_comment = 1`. Status
comments are listed (P5) but never queued, assessed or counted. Review bodies and threads are unchanged.

**N5 Follows primary (C15):** `decision_follows_primary` = linked, no gates, kind ≠ `pr_question`, state not
reopened/asked_back, not gone, and the item's own effect plan for the primary's current decision succeeds (dry run).
Gate items are always decided individually (RQ4/RQ5).
- On a decision (F-10): the planning closure of `decide_planned` appends, for each follower whose current decision is
  absent or itself `FollowsPrimary`, a `NewDecision` with the primary's kind/target/reason, `via = FollowsPrimary`,
  `follows = primary`, the follower's **own** effects (`effects::plan` on its item). Same transaction, so nothing is
  planned on stale state. A follower the owner decided individually stops following.
- Later links (F-11): after `finish_with_primary` commits, the pass calls `propagate(pr)` = `decide_planned` with
  only follower rows; idempotent, retried at the next pass or decision on failure (warn).
- Undo/supersede of the primary repeats on its followers in the same transaction.

**N6 Storage:** `comment_decision_origins(decision_id PK → comment_decisions ON DELETE CASCADE, origin
'imported_github'|'follows_primary', primary_decision_id, by_login, recorded_at, evidence_url, quote)`, append-only.
The stored `via` column keeps `question` for these rows; the wire `via` is derived from the origin. This avoids
rebuilding `comment_decisions` and its five children for a CHECK change (F-12).

## 7. Imported GitHub decisions (C11)

| ID | Rule |
|---|---|
| I1 | **Source:** the primary assessment's `recorded_decision` after host grounding (F-9: comment URL, author and verbatim quote verified against the read). The LLM proposes; the server decides whether it binds. |
| I2 | **Authority** (proposed, OQ6): (a) a tenant member's own statement (maintainers = member logins); (b) a relay listed in `SR_MAINTAINER_DELEGATES` whose quote names a maintainer (`on_behalf_of`); (c) the item's author withdrawing their own point (→ reject). Nothing else imports (bots and other people stay evidence). Reuses `binding_decision` (F-9). |
| I3 | **Topic guard** (C21 vs C51): the evidence comment must be in the item's own thread, or for body/PR-comment items a later comment that links or quotes that item; and written after the item (`written.at`). A decision on an older, similar point never decides a new item. |
| I4 | **Import:** only for an item without a current decision, inside the `propagate` transaction (N5): a decision `via = ImportedGithub`, user = the maintainer (named principal for relays), **no effects** (OQ5), state Decided; then followers propagate (N5). The owner can undo or decide again (supersedes). |
| I5 | **Kind:** recorded `deferred` → `todo`, `withdrawn` → `reject`, else the recorded kind; targets copied when present. |

Needs owner confirmation: OQ5 (effects) and OQ6 (authority list, relays, LLM-classified kind).

## 8. LLM activity (C7)

- Source: jobs not ended (`queued`, `claimed`, `running`, `paused`), server-wide; read by one query in
  `db::repo::jobs`. **Own** = `spec.payer` is the reader: kind, subject (`My work` → `/`; PR → `/pr/o/r/n` or its
  Comments page; Ask → the analysis), `since`/`queued_at`, `waits_for`. **Other** jobs: `owner: other`, kind only,
  `subject: null`, `id` = an opaque per-response index (never the job id, user, tenant or repository).
- `waits_for`: `UsageLimit { until }` from the payer pause (`resumes_at`), `AnalysisRunning` for a ranking held by
  OD12, else `Runner` while queued. `paused_until` = the reader's payer pause; `last_call` = Settings' `llm_status`.
- SSE: the job executor's state changes tick a broadcast; each `/api/v1/events` stream sends its user's snapshot at
  most once a second. Sessions and read tokens may read it (READ); no write route.

## 13. Risks

| ID | Risk | Mitigation |
|---|---|---|
| RB1 | Forged or replayed webhook requests | WAF allow-list; HMAC before parse; dedupe; events are only "re-read" signals, never data we trust |
| RB2 | Lost events leave facts stale | W4 retries, W11 sweep, nightly scan, manual Refresh; UI says "Live" only where configured |
| RB3 | CI bursts spend the user's GitHub points | 10 s coalescing per user, `REREAD_LIMIT`, existing rate-limit memory; check_suite not check_run |
| RB4 | Needs-you drift between web and server | N3 shared fixture in both test suites; web reads the server count (B15) |
| RB5 | An imported decision misread by the LLM | verified quote, authority list, topic guard, no effects, visible "imported" tag, undo |
| RB6 | Propagation decides the wrong items | gates excluded, own effect plans, owner's individual decision wins, undo cascades, tests |
| RB7 | B1 is a large contract change while web types are provisional | neutral values first; B15 is the single cut-over; generated artifacts checked |
| RB8 | Restarting finished rankings shows the snapshot's refresh as `ranking` again | expected: U3 lists the ranking job; summary revision changes; covered by B7 tests |
| RB9 | `json_each` over snapshots grows with users | measured at B3; index table only if needed |
