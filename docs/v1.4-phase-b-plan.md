## 2. Webhooks (ADR-026)

### 2.1 Path and endpoint
GitHub → Cloudflare WAF (GitHub `hooks` ranges only) → atlas tunnel → traefik (Host rewritten, real IP only in
`Cf-Connecting-IP`) → **webhook listener** `SR_WEBHOOK_LISTEN_ADDR` (default `127.0.0.1:3002`) → `POST /webhooks/github`
(public URL `https://webhooks.manago.cloud/diffpilot/github`). Route `githubWebhook` in `ROUTES` with
`RouteAuth::GithubSignature` and a new **`Listener::Webhook`** (SEC-002; the runner listener is the precedent): that
listener serves only this route (everything else 404), and the public UI/API listener keeps `/webhooks/*` at 404, so
a traefik matcher bypass cannot reach the UI/API through the webhook path. Not under `/api/`, no session, no CSRF,
never a personal access token. **The WAF is not authentication**: GitHub's hook ranges deliver any GitHub user's
webhooks to any URL, so only W1 (HMAC and App target) and W13 (tracked repositories) decide what is processed.

| ID | Rule |
|---|---|
| W1 | **Order** (SEC-003, SEC-013): headers and `Content-Length` are checked before any body byte is read — method POST → secret configured (else 503, W8) → `Content-Type: application/json` (else 415) → `Content-Length` present and ≤ **4 MiB** (route-level `DefaultBodyLimit` of 4 MiB; axum's default is 2 MB; 413) → `X-GitHub-Event`, `X-GitHub-Delivery` (UUID) present (else 400) → **exactly one** `X-Hub-Signature-256` header of the form `sha256=` + 64 lowercase hex (else 401) → body read under the 8 s timeout (W6) → HMAC-SHA256 over the raw bytes with the current secret, then the previous one if set (W8), constant-time `aws_lc_rs::hmac::verify` → 401 on mismatch, no detail → `X-GitHub-Hook-Installation-Target-Type` = `integration` and `X-GitHub-Hook-Installation-Target-ID` = `SR_GITHUB_APP_ID` (else 401; SEC-001) → only then parse JSON. IPs are never used for auth. Every answer before the full body read follows W14. |
| W2 | **Dedupe and durability:** in one write transaction insert `github_deliveries(delivery_id, body_sha256, …, state='pending')`. Existing row in `done`/`ignored` → 200, nothing else (duplicate). Existing `pending`/`failed` → processed again (GitHub redelivery reuses the delivery id and body, so a failed processing must stay retryable). **Replay guard (SEC-011):** a body whose SHA-256 matches a row of the last 14 days under another delivery id → 200 `duplicate`, debug log (the signature covers the body only; the GUID is unsigned). |
| W3 | **Fast ack:** the handler stores the delivery's typed `WebhookChange` list (extracted from the payload at receipt: repo, head repository, number, kind, head SHA, action, installation id) — never the raw payload — answers **202** and wakes the worker (tokio `Notify`). Target < 1 s; GitHub's limit is 10 s. |
| W4 | **Worker:** one in-process task drains `pending` rows oldest first, retries a failed row 3× with backoff (10 s, 1 min, 10 min), then `failed` (warn once). At start-up it resumes `pending`/`failed` rows younger than 3 days. |
| W5 | **`ping`:** 200, `ignored`, info log with hook id and the subscribed events it lists. Unknown events and actions the table §2.2 does not use: 202, `ignored`, debug log. |
| W6 | **Load (SEC-003):** on the webhook listener `HandleErrorLayer` + `LoadShedLayer` + `ConcurrencyLimitLayer(8)` + an 8 s `TimeoutLayer` covering the body read; a full handler answers **503** at once (GitHub records a failed delivery; no redelivery, W10). The listener sets an HTTP/1 header-read timeout (5 s). The 503 of load shedding and of the timeout layer drains the body first (W14). |
| W7 | **Logging/audit (SEC-013):** info per accepted delivery (`delivery_id`, event, action, installation id, repo, number, outcome `queued`/`duplicate`/`ignored`/`not_allowed` (not tracked)); warn on signature failure at most once a minute (counter in the message), with `Cf-Connecting-IP` only as a parsed `IpAddr` (never the raw header, never fed into the request's `client_address`); never the body, signature, secret or any payload text — the `error` column and warnings hold typed codes only. Rows kept 14 days (pruned by the nightly task); `GET /api/v1/settings/github-webhook` shows the last verified delivery time. |
| W8 | **Secret config:** `SR_GITHUB_WEBHOOK_SECRET` (already in the owner's `secrets.env`, 64 hex characters; loaded as `SecretString`, rejected at start-up only when present but shorter than 32 characters). **Absent:** the server starts normally, logs once at start-up (warn: "GitHub webhook secret not set; repositories are not live, only Refresh and the nightly scan update My work"), `POST /webhooks/github` answers **503** `webhook_not_configured` after draining the body (W14). Repositories are not live while the secret is absent. 503 (not 404) so GitHub's delivery log shows a server-side failure. **Rotation (SEC-012):** optional `SR_GITHUB_WEBHOOK_SECRET_PREVIOUS`, verified after the current secret fails (debug log names which matched); runbook order: (1) set PREVIOUS = old, SECRET = new, restart; (2) change the secret in the GitHub App; (3) once a delivery verified with the new secret is logged, remove PREVIOUS and restart; deliveries lost in between are covered by W10. `SR_GITHUB_WEBHOOK_URL` (optional, https, display only in Settings › GitHub sync; absent = Settings shows no URL). Content type `application/json` only (the App is configured so). |
| W13 | **Tracked repositories only (SEC-001, owner 2026-11-25):** the App `claudbot` (id 5133300) is public, so any GitHub account can install it and send correctly signed events. Besides W1's App-id and target-header checks, a delivery is processed only when its repository (matched by numeric repository id where the event carries one, else owner/name) is **tracked by at least one tenant**: (a) its owner is in a tenant user's "Owners to list" (`DashboardSettings.enumerate_owners`, `crates/server/src/dashboard/settings.rs:177`), (b) it is in a tenant user's repository rules, (c) a PR of it is watched or analysed by a tenant user, or (d) the PR/issue is in a tenant user's current snapshot (added to the owner's list: such an item shows `live`, so its events must count). Everything else → **202**, state `not_allowed` (= not tracked), nothing processed, counted, info log once per repository and day. No environment allow-list. `installation` / `installation_repositories` events only refresh the live map (`app_repositories`) for tracked repositories; untracked repositories are never stored (the 2,000-row cap stays as a safety net). Settings › GitHub sync shows, per tenant, which of its tracked repositories are live (C3) and the installation-wide count of dropped deliveries in 14 days (C13). |
| W14 | **Drain before an early answer** (owner evidence 2026-11-25, `/data/artifacts/diffpilot/2026-11-25/v14/infra/webhook-502-repro.md`): ~40 % of live deliveries got 502 from traefik because the server answered `/webhooks/*` (404) before reading the body and closed the connection while traefik was still streaming it — closing a socket with unread received data sends a TCP RST, and the proxy loses the answer. Rule: every answer sent before the handler consumed the body — 400, 401 (header checks), 404 (any path on the webhook listener other than the route, and the `/webhooks/*` catch-all on the public listener, `crates/server/src/frontend/mod.rs:43`), 405, 411, 415, 503 (no secret, load shed, timeout) — is written only after the rest of the body was read and discarded into a fixed buffer (no allocation per request), up to 4 MiB, within the 8 s body timeout. One outermost layer `drain_unread_body` on each listener for those paths does it for all answers, including the ones produced by inner layers. `Content-Length` > 4 MiB → 413 with `Connection: close` at once, no draining; a chunked body that passes 4 MiB or a drain that hits the timeout → stop and answer with `Connection: close`. The drain holds no handler slot (W6). |

### 2.3 Processing (idempotent signals, never state)
An event is a signal "re-read this"; processing always re-reads GitHub, so order and duplicates do not matter
(cost only). Per user, signals are coalesced in a **fixed 10 s window** opened by the first signal and never extended (SEC-005: a steady stream cannot starve the read), then:

| ID | Rule |
|---|---|
| P-1 | **Affected users:** users whose current snapshot holds the PR/issue (SQLite `json_each` over the current snapshots; few users; add an index table only if profiling asks). Check/status events match `StoredPr` by **(repository or head repository, head SHA)** (SEC-001: a fork at the same SHA in another repository matches nothing). |
| P-2 | **Dashboard:** `reread` of those PRs (existing path, user token, `REREAD_LIMIT`, rate-limit memory), extended to issues (B3). Facts only (P3): the snapshot changes, the judgement's fingerprint no longer matches → *outdated* (§4). **Budget (SEC-005):** event-driven reads of a user spend at most 1,000 GitHub points per hour (counted from the reads' reported cost) and stop while the user's remaining rate limit is below 1,000; skipped items are listed in the log and wait for the next event, Refresh or the nightly scan. |
| P-3 | **New items (OQ4 = b):** E1 `review_requested`/`assigned`/`opened` naming a linked login of a user, for a PR not in the snapshot → read that PR; **the relation comes from that re-read** (requested reviewers, assignees, author) and must pass the user's scan rules (repositories, skipped authors) — the event's own fields decide nothing (SEC-001); then `rank_pending` judges it as a new item **through K3** (daily cap): at zero room no job is submitted and the item shows `capped`; at most **20** event-added items per user and local day (SEC-005). |
| P-4 | **Review loop:** a watched PR (any watcher) in a live repository gets the watch probe **only from events** (owner OQ3, 2026-11-25: no periodic probe there), **coalesced per PR with at least 60 s between probes** (SEC-005: outsiders can create comment and CODEOWNERS `review_requested` events on public repositories), so a pass becomes due by the existing rules (bot-round wait, spacing, daily cap). Watched PRs in repositories without the App: the scheduler probes them **once an hour** (was every 5 min, F-17). Unwatched PRs: nothing (Comments reads on demand). |
| P-5 | **Live set:** E11 upserts/removes `app_repositories` rows of tracked repositories (W13); `suspend` marks suspended. A daily sync (nightly task) and a lookup when a tracked repository is new use `GET /repos/{o}/{n}/installation` (App JWT, `github/app_token.rs:224-244`) — no new token type. |
| P-6 | **Live:** a repository is live when the webhook is configured (W8), it is tracked (W13) and in `app_repositories`, not suspended. TODO items have no `live`. |

## 4. Judgement model (C1, C2, G2)

| ID | Rule |
|---|---|
| J1 | **Queue** (every ranking: manual, nightly, webhook, re-judge): asked items **never judged** (no stored body), plus items with a re-judge request, plus — only for `rejudge_outdated` — every outdated item. Changed items are no longer queued (replaces F-3). Order: requests first, then new by provisional score. |
| J2 | **Outdated:** a stored judgement that is not fresh; `prompt_changed` when prompt or input version differ (`older`), else `facts_changed`. It keeps scoring as `Inherited` (today's behaviour). |
| J3 | **Re-judge request:** `dashboard_judgements.rejudge_requested_at` (B1 migration). Set by C2 (one item) or by `rejudge_outdated` (all outdated); cleared when the new judgement is saved (the row is replaced). Persisting it survives restarts and makes `judging` derivable. |
| J4 | **Ranking without a scan** (`refresh::rank_pending(scope)`): when nothing is live, restart the ranking of the current snapshot's refresh in a new attempt (F-5 widened to rankings that ended `finished`); when a ranking is live, it **drains**: before finishing it re-reads pending requests and new items and judges them in the same attempt. Used by C2, webhooks (P-3) and the end of a re-read that added items. |
| J5 | **States:** current = fresh; judging = request pending and a ranking live; outdated = not fresh otherwise; queued = never judged and a ranking live; capped = never judged and in the latest ranking's left-provisional keys (stored in `RefreshProgress.left_provisional_keys`, serde default, no migration); not_judged = never judged otherwise. |
| J6 | **Nightly** (ADR-020) uses J1 without `rejudge_outdated`: it judges only never-judged items (U19). A prompt bump makes every judgement `prompt_changed`, re-judged only by click or "Refresh and re-judge outdated". |
| J7 | **Counts:** `status_counts` from the scored items: outdated (J5 outdated + judging), not_judged (queued + capped + not_judged), not_live (C3), excluded (existing exclusions total). |

## 6. Needs you (C10) and duplicates (C15)

**N1 Item status** — a Rust port of `web/src/components/comments/queueStatus.ts` `commentStatus` (first match wins);
`awaits` = not gone and state ∈ {undecided, reopened, asked_back}; `linked` = `duplicate_of` set and ≠ own number:
1. `status_comment` → StatusComments
2. current decision `ImportedGithub`, or state `outside` → Decided
2a. active **not-a-review-point** mark (C19, §7a) → NotAReviewPoint (new queue status, listed with its count, never Needs you)
3. `decision_follows_primary` (linked, no gates) → Duplicates
4. state ∈ {decided, executing, done, repeat} → Decided
5. gone → All
6. linked and (awaits, or gates non-empty and state `assessing`) → **NeedsYou** (unassessed linked items without C15 count)
7. assessment Queued → Waiting; 8. Running → Assessing
9. kind ≠ `pr_question` and NotAssessed → NotAssessed (unassessed unlinked items do not count)
10. awaits → **NeedsYou**, else All

**N2 Count** = Σ over the overview's queue entries of their items whose status is NeedsYou (items outside the queue
never count, as `needsYouQueue`); `needs_you_gates` = those with gates. One function in `review_loop::queue`
feeds `CommentCounts`, the PR page summary, the PR state badge B2 `QuestionsWaiting` (review plan §3.9, not WP B2) and the dashboard tally (F-6 SQL keeps `total`, `was_read`,
`watched`; `needs_you` is computed from the loaded views of the listed PRs that were read).
**N3 Drift guard:** a checked-in fixture `docs/contracts/fixtures/needs-you-cases.json` (items, queue → expected
status per item and count) runs in a Rust test and a vitest test; B15 points the web at the server count.

**N4 Status comments (F1/F2 of 07b69073):** an item from the source fallback (F-7) whose author is a bot — `Bot`
typename, `[bot]` login or `known_bots` (fixes F2: today `__typename` is ignored there) — of kind `pr_comment`, with
no finding markers (`markers::body_findings` empty, no `finding_marker`), is stored with `status_comment = 1`. Status
comments are listed (P5) but never queued, assessed or counted. Review bodies and threads are unchanged.
*Case dashpay/tenderdash#1600 C9* (owner TODO `81a75cdb`; inferred from the public PR — the item number was not
checked against the production database): the only bot PR comment left as a question is CodeRabbit's "Review
skipped — Auto reviews are disabled on this repository" status message (`coderabbitai[bot]`, `__typename Bot`;
the thepastaclaw gate comment and the `platform-pr-review-state-v1` comments are already Ignored by `handin::role`).
Cause, three steps of F-7: `observe` skips the bot comment (`observe.rs:552-565`), `handin::role` classifies it as
Source (no ignore rule matches, `handin.rs:22-54`), and the source fallback stores it as a **human** item because
it decides bot-ness from the login only (`known_bots` or a `[bot]` suffix; GraphQL gives `coderabbitai` without the
suffix, `review_loop/mod.rs:445-453`). The N4 rule catches it deterministically once the fallback carries the
author's `__typename` (B9 test `coderabbit_review_skipped_is_status_comment`); C19 is for what no rule catches.

**N5 Follows primary (C15):** `decision_follows_primary` = linked, no gates, kind ≠ `pr_question`, state not
reopened/asked_back, not gone, and the item's own effect plan for the primary's current decision succeeds (dry run).
Gate items are always decided individually (RQ4/RQ5).
- On a decision (F-10): the planning closure of `decide_planned` appends, for each follower whose current decision is
  absent or itself `FollowsPrimary`, a `NewDecision` with the primary's kind/target/reason, `via = FollowsPrimary`,
  `follows = primary`, the follower's **own** effects (`effects::plan` on its item). Same transaction, so nothing is
  planned on stale state. A follower the owner decided individually stops following.
- Later links (F-11): after `finish_with_primary` commits, the pass calls `propagate(pr)` = `decide_planned` with
  only follower rows; idempotent, retried at the next pass or decision on failure (warn).
- Undo/supersede of the primary repeats on its followers in the same transaction.
- **Imports propagate only for authority (a)/(b) of §7** (SEC-008). A withdrawal by an item's author (c) decides only that author's own items and never their followers by other authors: an outsider who posts a near-copy, becomes the primary and withdraws it cannot reject a real reviewer's finding.

**N6 Storage:** `comment_decision_origins(decision_id PK → comment_decisions ON DELETE CASCADE, origin
'imported_github'|'follows_primary', primary_decision_id, by_login, by_github_id, relay_login, recorded_at, evidence_url, quote)`, append-only. Imported rows require evidence. Followers reference another item's decision in the same tenant and PR.
The stored `via` column keeps `question` for these rows; the wire `via` is derived from the origin. This avoids
rebuilding `comment_decisions` and its five children for a CHECK change (F-12).
