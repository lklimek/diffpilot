## 2. Webhooks (ADR-026)

### 2.1 Path and endpoint
GitHub → Cloudflare WAF (GitHub `hooks` ranges only) → atlas tunnel → traefik (Host rewritten, real IP only in
`Cf-Connecting-IP`) → **webhook listener** `SR_WEBHOOK_LISTEN_ADDR` (default `127.0.0.1:3002`) → `POST /webhooks/github`
(public URL `https://webhooks.manago.cloud/diffpilot/github`). Route `githubWebhook` in `ROUTES` with
`RouteAuth::GithubSignature` and a new **`Listener::Webhook`** (separate ingress as with the runner listener): that
listener serves only this route (everything else 404), and the public UI/API listener keeps `/webhooks/*` at 404, so
a traefik matcher bypass cannot reach the UI/API through the webhook path. Not under `/api/`, no session, no CSRF,
never a personal access token. **The WAF is not authentication**: GitHub's hook ranges deliver any GitHub user's
webhooks to any URL, so only W1 (HMAC and App target) and W13 (tracked repositories) decide what is processed.

| ID | Rule |
|---|---|
| W1 | **Order and limits** (W6, W14): headers, including `Content-Length` when supplied, are checked before any body byte is read — method POST → secret configured (else 503, W8) → `Content-Type: application/json` (else 415) → an advertised `Content-Length` above **4 MiB** → 413 with connection close (chunked bodies are accepted and use the same 4 MiB body limit and 8 s timeout) → `X-GitHub-Event`, `X-GitHub-Delivery` (UUID) present (else 400) → **exactly one** `X-Hub-Signature-256` header of the form `sha256=` + 64 lowercase hex (else 401) → body read under the 8 s timeout (W6) → HMAC-SHA256 over the raw bytes with the current secret, then the previous one if set (W8), constant-time `aws_lc_rs::hmac::verify` → 401 on mismatch, no detail → `X-GitHub-Hook-Installation-Target-Type` = `integration` and `X-GitHub-Hook-Installation-Target-ID` = `SR_GITHUB_APP_ID` (else 401) → only then parse JSON. IPs are never used for auth. Every answer before the full body read follows W14. |
| W2 | **Dedupe and durability:** in one write transaction insert `github_deliveries(delivery_id, body_sha256, …, state='pending')`. Existing row in `done`/`ignored` → 200, nothing else (duplicate). Existing `pending`/`failed` → processed again (GitHub redelivery reuses the delivery id and body, so a failed processing must stay retryable). **Replay guard (RB1):** a body whose SHA-256 matches a row of the last 14 days under another delivery id → 200 `duplicate`, info log (the signature covers the body only; the GUID is unsigned). |
| W3 | **Fast ack:** the handler stores the delivery's typed `WebhookChange` list (extracted from the payload at receipt: repo, head repository, number, kind, head SHA, action, installation id) — never the raw payload — answers **202** and wakes the worker (tokio `Notify`). Target < 1 s; GitHub's limit is 10 s. |
| W4 | **Worker:** one in-process task drains `pending` rows in order of eligibility, retries failed work 3× with backoff (10 s, 1 min, 10 min), then records it as `failed` (warn once). Once routed, the queue keeps only unfinished destinations; a failed destination does not replay the others. At start-up it resumes `pending`/`failed` rows younger than 3 days. Already scheduled destinations keep their eligibility time. |
| W5 | **`ping`:** 200, `ignored`, info log with hook id and the subscribed events it lists. Unknown events and actions the table §2.2 does not use: 202, `ignored`, debug log. |
| W6 | **Load:** on the webhook listener `HandleErrorLayer` + `LoadShedLayer` + `ConcurrencyLimitLayer(8)` + an 8 s `TimeoutLayer` covering the body read; a full handler answers **503** at once (GitHub records a failed delivery; no redelivery, W10). The listener sets an HTTP/1 header-read timeout (5 s). The 503 of load shedding and of the timeout layer drains the body first (W14). |
| W7 | **Logging/audit:** info per accepted delivery (`delivery_id`, event, action, installation id, repo, number, outcome `queued`/`duplicate`/`ignored`/`not_allowed` (not tracked)); warn on signature failure at most once a minute (counter in the message), with `Cf-Connecting-IP` only as a parsed `IpAddr` (never the raw header, never fed into the request's `client_address`); never the body, signature, secret or any payload text — the `error` column and warnings hold typed codes only. Rows kept 14 days (pruned by the nightly task); `GET /api/v1/settings/github-webhook` shows the last verified delivery time. |
| W8 | **Secret config:** `SR_GITHUB_WEBHOOK_SECRET` (already in the owner's `secrets.env`, 64 hex characters; loaded as `SecretString`, rejected at start-up only when present but shorter than 32 characters). **Absent:** the server starts normally, logs once at start-up (warn: "GitHub webhook secret not set; repositories are not live, only Refresh and the nightly scan update My work"), `POST /webhooks/github` answers **503** `webhook_not_configured` after draining the body (W14), without verifying or parsing it, no repository is live. 503 (not 404) so GitHub's delivery log shows a server-side failure. **Rotation:** optional `SR_GITHUB_WEBHOOK_SECRET_PREVIOUS`, verified after the current secret fails (debug log names which matched); runbook order: (1) set PREVIOUS = old, SECRET = new, restart; (2) change the secret in the GitHub App; (3) once a delivery verified with the new secret is logged, remove PREVIOUS and restart; deliveries lost in between are covered by W10. `SR_GITHUB_WEBHOOK_URL` (optional, https, display only in Settings › GitHub sync; absent = Settings shows no URL). Content type `application/json` only (the App is configured so). |
| W13 | **Tracked repositories only (owner 2026-11-25):** the App `claudbot` (id 5133300) is public, so any GitHub account can install it and send correctly signed events. Besides W1's App-id and target-header checks, a delivery is processed only when its repository (matched by numeric repository id where the event carries one, else owner/name) is **tracked by at least one tenant**: (a) its owner is in a tenant user's "Owners to list" (`DashboardSettings.enumerate_owners`, `crates/server/src/dashboard/settings.rs:177`), (b) it is in a tenant user's repository rules, (c) a PR of it is watched or analysed by a tenant user, or (d) the PR/issue is in a tenant user's current snapshot (added to the owner's list: such an item shows `live`, so its events must count). Tracking is checked in a read transaction before taking the write lock. An untracked delivery answers **202**, increments a bounded in-process counter and logs at info once per repository and day. It writes no delivery row. No environment allow-list. `installation` / `installation_repositories` events only refresh the live map (`app_repositories`) for tracked repositories. The receiver filters repository lists as a batch and processes up to 500 matching entries per list. The live map stores up to 2,000 rows. Settings › GitHub sync shows, per tenant, which of its tracked repositories are live (C3) and the installation-wide count of dropped deliveries since the last restart, at most 14 days (C13). |
| W14 | **Drain before an early answer** (owner evidence 2026-11-25, `/data/artifacts/diffpilot/2026-11-25/v14/infra/webhook-502-repro.md`): ~40 % of live deliveries got 502 from traefik because the server answered `/webhooks/*` (404) before reading the body and closed the connection while traefik was still streaming it — closing a socket with unread received data sends a TCP RST, and the proxy loses the answer. Rule: every answer sent before the handler consumed the body — 400, 401 (header checks), 404 (any path on the webhook listener other than the route, and the `/webhooks/*` catch-all on the public listener, `crates/server/src/frontend/mod.rs:43`), 405, 415, 503 (no secret, load shed, timeout) — is written only after the rest of the body was read and discarded into a fixed buffer (no allocation per request), up to 4 MiB, within the 8 s body timeout. One outermost layer `drain_unread_body` on each listener for those paths does it for all answers, including the ones produced by inner layers. `Content-Length` > 4 MiB → 413 with `Connection: close` at once, no draining; a chunked body that passes 4 MiB or a drain that hits the timeout → stop and answer with `Connection: close`. The drain holds no handler slot (W6). |

### 2.3 Processing (idempotent signals, never state)
An event is a signal "re-read this"; processing always re-reads GitHub, so order and duplicates do not matter
(cost only). Per user, signals are coalesced in a **fixed 10 s window**. The first signal opens it and later signals leave the deadline fixed (RB3). The worker then dispatches as follows.

| ID | Rule |
|---|---|
| P-1 | **Affected users:** users whose current snapshot holds the PR/issue (SQLite `json_each` over the current snapshots; few users; add an index table only if profiling asks). A check that names a PR with its base repository can match by **(base repository, number)** even with a stale stored head, provided the event repository matches the base or head repository. SHA-only hints match by **(repository or head repository, head SHA)** (RB1). |
| P-2 | **Dashboard:** `reread` of those PRs (existing path, user token, `REREAD_LIMIT`, rate-limit memory), extended to issues (B3). While a scan is running, one durable carrier per dashboard merges all affected items. Each hold starts when the dashboard is first blocked, and another check becomes eligible by the scan timeout plus the coalescing window. If the scan is still running at expiry, a new hold begins without consuming a W4 retry. Existing PRs and issues keep their scan relations. Fact changes can make the judgement *outdated* (§4). **Budget (RB3):** event-driven reads of a user spend at most 1,000 GitHub points per hour (counted from the reads' reported cost) and stop while the user's remaining rate limit is below 1,000; skipped items are listed in the log and wait for the next event, Refresh or the nightly scan. |
| P-3 | **New items (OQ4 = b):** E1 `review_requested`/`assigned`/`opened` naming a linked login of a user, for a PR not in the snapshot → read that PR; **the relation comes from that re-read** (requested reviewers, assignees, author) and must pass the user's scan rules (repositories, skipped authors) (RB1); then `rank_pending` judges it as a new item **through K3** (daily cap): at zero room no job is submitted and the item shows `capped`; at most **20** event-added items per user and local day (RB3). |
| P-4 | **Review loop:** a watched PR (any watcher) in a live repository gets the watch probe **only from events** (owner OQ3, 2026-11-25: no periodic probe there), **coalesced per PR with at least 60 s between probes** (RB3: outsiders can create comment and CODEOWNERS `review_requested` events on public repositories), so a pass becomes due by the existing rules (bot-round wait, spacing, daily cap). Event probes and each GraphQL page of the full review read share the P-2 budget and rate-limit floor. Spacing and rate limits park one durable carrier per PR, preserving review signals from every merged delivery. Each hold starts when work first blocks, and another check becomes eligible within 65 minutes. Continued deferral does not consume a W4 retry. Watched PRs in non-live repositories: the scheduler probes them **once an hour** (was every 5 min, F-17). Unwatched PRs: nothing (Comments reads on demand). |
| P-5 | **Live set:** E11 upserts/removes `app_repositories` rows of tracked repositories (W13); `suspend` marks suspended. A daily sync (nightly task) and a lookup when a tracked repository is new use `GET /repos/{o}/{n}/installation` (App JWT, `github/app_token.rs:224-244`) — no new token type. |
| P-6 | **Live:** a repository is live when the webhook is configured (W8), it is tracked (W13) and in `app_repositories`, not suspended. TODO items have no `live`. |

## 4. Judgement model (C1, C2, G2)

| ID | Rule |
|---|---|
| J1 | **Queue.** A scan or event ranking includes asked items without a stored judgement and eligible C2 requests. Bulk re-judge allocates room to C2 requests and new items first, then selects outdated items for the remaining room. The send order is C2 requests, selected bulk requests, then new items by provisional score. A dedicated C2 ranking takes only its accepted clicks. |
| J2 | **Outdated:** a stored judgement that is not fresh; `prompt_changed` when prompt or input version differ (`older`), else `facts_changed`. It keeps scoring as `Inherited` (today's behaviour). |
| J3 | **Re-judge request.** C2 persists the clicked item in `dashboard_judgements.rejudge_requested_at` until its replacement is saved. A second click while that item is judging returns 202 for the existing request. Bulk selection records only the chosen keys in the scan attempt's progress. Each replacement clears its key and unsent bulk selections expire with the attempt. |
| J4 | **Ranking without a scan.** If idle, restart the current snapshot's refresh in a new attempt, including after a successful ranking. A C2 restart covers only the clicked item and any further C2 requests accepted while it ranks. `rank_pending(scope)` serves new event items and pending C2 work. A live ranking re-reads its queue before finishing. Accepted clicks that have yet to be dispatched can start a dedicated attempt after the active one ends. |
| J5 | **States.** A fresh judgement is `current`. An older judgement is `judging` while a live ranking covers its replacement and `outdated` otherwise. A never-judged item is `queued` if a live ranking covers it, `capped` if named by `RefreshProgress.left_provisional_keys`, or `not_judged` otherwise. |
| J6 | **Nightly** (ADR-020) and plain Refresh admit never-judged items and genuine pending C2 requests under the scan caps. A prompt bump marks stored judgements `prompt_changed` and they are eligible for explicit re-judge. |
| J7 | **Counts:** `status_counts` from the scored items: outdated (J5 outdated + judging), not_judged (queued + capped + not_judged), not_live (C3), excluded (existing exclusions total). |

## 5. Ranking caps (G3)

| ID | Rule |
|---|---|
| K1 | **Ledger** `dashboard_sends(id, tenant_id, user_id, refresh_id, attempt, items, job_id, sent_at, released_at)` replaces `dashboard_refreshes.sent` (left dormant). Reservation (same write transaction and fence as today) inserts a row; per-refresh total = Σ items of the refresh; day total = Σ items with `sent_at ≥ max(day_start, reset_at)` and `released_at IS NULL`. Counting by send time fixes F-4's "whole refresh on every day" and lets a re-judge of yesterday's snapshot count only today's sends. B1 migration back-fills rows from `sent` of refreshes started in the last 48 h. |
| K2 | **Refund (e1f41101):** a failed or cancelled judge job releases its row (`released_at`, info log) if it reported no input or output tokens, regardless of `llm_call` (F-16). Test: five failed-before-provider batches leave the next refresh's room at 120. |
| K3 | **Re-judge caps.** Every send in a scan ranking, including its drain and all requests, counts against both the per-refresh cap (48) and the daily cap. Dedicated C2 and event rankings on an existing snapshot use the daily cap. A dedicated C2 ranking sends only accepted single-item requests. |

## 6. Needs you (C10) and duplicates (C15)

**N1 Item status** — a Rust port of `web/src/components/comments/queueStatus.ts` `commentStatus` (first match wins);
`awaits` = not gone and state ∈ {undecided, reopened, asked_back}; `linked` = `duplicate_of` set and ≠ own number:
1. `status_comment` → StatusComments
2. current decision `ImportedGithub`, or state `outside` → Decided
2a. active **not-a-review-point** mark (C19, §7a) → NotAReviewPoint (new queue status, listed with its count, never Needs you)
3. `decision_follows_primary` (linked, no gates) → Duplicates
4. state ∈ {decided, executing, done, repeat} → Decided
5. gone → All
6. linked and (awaits, or gates non-empty and state `assessing`) → **NeedsYou** (unassessed linked items without C15 count)
7. assessment Queued → Waiting; 8. Running → Assessing
9. kind ≠ `pr_question` and NotAssessed → NotAssessed (unassessed unlinked items do not count)
10. awaits → **NeedsYou**, else All

**N2 Count** = Σ over the overview's queue entries of their items whose status is NeedsYou (items outside the queue
never count, as `needsYouQueue`); `needs_you_gates` = those with gates. One function in `review_loop::queue`
feeds `CommentCounts`, the PR page summary, the PR state badge B2 `QuestionsWaiting` (review plan §3.9, not WP B2) and the dashboard tally (F-6 SQL keeps `total`, `was_read`,
`watched`; `needs_you` is computed from the loaded views of the listed PRs that were read).
**N3 Drift guard:** a checked-in fixture `docs/contracts/fixtures/needs-you-cases.json` (items, queue → expected
status per item and count) runs in a Rust test and a vitest test; B15 points the web at the server count.

**N4 Status comments (F1/F2 of 07b69073):** an item from the source fallback (F-7) whose author is a bot — `Bot`
typename, `[bot]` login or `known_bots` (fixes F2: today `__typename` is ignored there) — of kind `pr_comment`, with
no finding markers (`markers::body_findings` empty, no `finding_marker`), is stored with `status_comment = 1`. Status
comments are listed (P5) but never queued, assessed or counted. Review bodies and threads are unchanged.
*Case dashpay/tenderdash#1600 C9* (owner TODO `81a75cdb`; inferred from the public PR — the item number was not
checked against the production database): the only bot PR comment left as a question is CodeRabbit's "Review
skipped — Auto reviews are disabled on this repository" status message (`coderabbitai[bot]`, `__typename Bot`;
the thepastaclaw gate comment and the `platform-pr-review-state-v1` comments are already Ignored by `handin::role`).
Cause, three steps of F-7: `observe` skips the bot comment (`observe.rs:552-565`), `handin::role` classifies it as
Source (no ignore rule matches, `handin.rs:22-54`), and the source fallback stores it as a **human** item because
it decides bot-ness from the login only (`known_bots` or a `[bot]` suffix; GraphQL gives `coderabbitai` without the
suffix, `review_loop/mod.rs:445-453`). The N4 rule catches it deterministically once the fallback carries the
author's `__typename` (B9 test `coderabbit_review_skipped_is_status_comment`); C19 is for what no rule catches.

**N5 Follows primary (C15):** `decision_follows_primary` = linked, no gates, kind ≠ `pr_question`, state not
reopened/asked_back, not gone, and the item's own effect plan for the primary's current decision succeeds (dry run).
Gate items are always decided individually (RQ4/RQ5).
- On a decision (F-10): the planning closure of `decide_planned` appends, for each follower whose current decision is
  absent or itself `FollowsPrimary`, a `NewDecision` with the primary's kind/target/reason, `via = FollowsPrimary`,
  `follows = primary`, thread-local reply and resolve effects. Run each fix, follow-up PR, upstream issue or TODO once on the
  primary. The primary effect lists all eligible duplicates known when the effect is claimed using GitHub links.
  Each follower reply links to the primary discussion and any public outcome, and waits for the artefact effect to succeed. A late link can extend pending
  work and can use an already completed outcome. Plan and store under one transaction. A follower the owner decided individually stops following.
- Later links (F-11): after `finish_with_primary` commits, the pass calls `propagate(pr)` = `decide_planned` with
  eligible imports and follower rows; idempotent. A later pass can retry both, while an owner's
  decision can retry only follower propagation.
- Undo and supersede close the old follow decisions in the same transaction. A follower with a live effect
  claim blocks both operations and the conflict names the item. Reopen and re-ask cancel the primary's and
  followers' unclaimed effects and put the affected items back in Needs you.
- Binding member imports propagate as passive decisions. A withdrawal concerns its own item and does not propagate.

**N6 Storage:** `comment_decision_origins(decision_id PK → comment_decisions ON DELETE CASCADE, origin
'imported_github'|'follows_primary', primary_decision_id, by_login, by_github_id, relay_login, recorded_at, evidence_url, quote)`, append-only. Imported rows require evidence. Followers reference another item's decision in the same tenant and PR.
The stored `via` column keeps `question` for these rows; the wire `via` is derived from the origin. This avoids
rebuilding `comment_decisions` and its five children for a CHECK change (F-12).

## 6a. Assessment starts only on an explicit trigger (owner 2026-11-25, C20)

Opening the PR main page must not start LLM work. Today every review-loop read that finds new comments queues a
pass: `ensure_read` requests `PassReason::NewComments` (`crates/server/src/review_loop/mod.rs:176-203`) and is

(`POST` RC3, `:270-278`); the overview `GET` also queues `PassReason::Opened` itself (`:256-266`).

| ID | Rule |
|---|---|
| A1 | **Reads never queue LLM work.** `ensure_read` keeps reading GitHub (the reader's token, `READ_INTERVAL`) but no longer requests a pass; the overview `GET` drops its `Opened` request. | A2 | **Explicit trigger (C20):** `POST …/comments/assess` = `request_pass_for(PassReason::Opened)` for the session user (daily pass cap, spacing and one pass per PR as today). | A4 | **After an agent's report** the follow-up read (`review_loop/seen.rs:78-97`) queues a pass only when the PR is watched (A3 rules); otherwise new items wait for the next Comments entry. (Same rule as A1; added by the architect, the owner named only the page read.) |
| A5 | Ask (`PassReason::Ask`) and "Assess again" (RC6) are explicit user actions and stay as they are. |
